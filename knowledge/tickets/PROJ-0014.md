# Use native date types end-to-end for planting_date and death_date

> **Workflow Status**: Requirements gathered ✓ → Ready for `/create_plan_generic` to research and plan

## Problem Statement & Business Context

**What problem are we solving?**

`planting_date` and `death_date` are stored and carried as free-form `str` (YYYY-MM-DD) through the domain and ORM layers, while the API response schemas already declare `date | None`. Consequences:

- The domain performs repeated `strptime` parsing just to *compare* dates (`plant.py:55,92,163,187`).
- The API request schema accepts a raw `str` (`PlantDeathRequest.death_date`, `schemas.py:8`), deferring format validation to domain strptime instead of Pydantic.
- The Postgres columns are `VARCHAR(10)`, relying on ISO-format discipline in every code path for ordering/range behavior.
- The review loop bounced the migration column type three times (`String(10)` → `sa.Date()` → `String(10)`, commits `d74cf96` / `00d0880` / `d639c80`) because each round reconciled the migration toward the ORM instead of deciding which representation is correct.

**Owner decision (Gerald, 2026-08-22): all date fields use native date types end-to-end** — `sa.Date()` in migrations, `Date()` + `Mapped[date]` in ORM, `date` objects in the domain, `date` in Pydantic schemas. This decision overrides "align with the ORM" review feedback: the ORM is what gets aligned, not the decision.

**Why is this important?**

Strong typing removes a whole class of format bugs, gives Postgres real `DATE` semantics (ordering, ranges, date math), and ends the review-loop thrash by recording an authoritative decision.

## Requirements & Scope

### In Scope

- `plants.planting_date` (NOT NULL) and `plants.death_date` (nullable) become native dates in **every** layer:

| Layer | File(s) | Change |
|---|---|---|
| Migration (death) | `alembic/versions/a1b2c3d4e5f6_add_death_fields_to_plant.py` | `death_date` → `sa.Date()` (in-place edit — **safe: verified 2026-08-22 that this revision has never been applied to any environment**; cluster `alembic_version` = `72fff22905dd`, local PG not running) |
| Migration (planting) | new forward migration | `ALTER TABLE plants ALTER COLUMN planting_date TYPE DATE USING planting_date::date` (cluster DB holds real data) |
| ORM (service tree) | `packages/plant_service/src/plant_service/adapters/repository/models/plant_model.py` | `planting_date: Mapped[date]`, `death_date: Mapped[Optional[date]]`, `Date()` columns |
| ORM (legacy CLI tree) | `commands/models/plant.py` | same two columns — this tree still maps the same table via `_get_db()` and MUST change in the same deployment |
| Domain | `packages/plant_service/src/plant_service/domain/plant.py` | `planting_date: date` (default `date.today()`), `death_date: date | None`; delete the strptime validation blocks; native comparisons (`death_date >= planting_date`, `death_date <= date.today()`); `generate_id` uses `.year` |
| Repository | `packages/plant_service/src/plant_service/adapters/repository/plant_repository.py` | remove strptime validation on create (lines ~27-38) |
| API request | `backend/fastapi/src/plant_tracking_api/schemas.py` | `PlantDeathRequest.death_date: date` (Pydantic validates; 422 on malformed input). Response schemas already `date \| None` — no change |
| CLI | `commands/plant_tracking_cli.py` | parse date inputs with `date.fromisoformat` (clear error on bad input); display via `isoformat()` |

- **Data guard**: before running the conversion migration, verify all existing `planting_date` values are well-formed ISO dates in the target database (query in planning phase); fail loudly if any are not.
- **Backlog closure**: update `knowledge/backlog/death-date-and-planting-date-are-typed-as-str-none-or-str.md` to record that this ticket is the resolution path, so future review rounds disposition it as "covered by PROJ-0014" instead of re-litigating.

### Out of Scope

- **Timestamp fields** `plant_log_entries.timestamp` and `media_attachments.timestamp` (`String(20)`, format `YYYY-MM-DDTHH:MM:SSZ`): same principle applies but the target type is `DateTime(timezone=True)`, not `sa.Date()`, and the blast radius differs (S3 keys, sorting, CLI display, legacy `commands/plant_log_model.py`). → separate follow-up ticket.
- `created_at` / `updated_at`: already `DateTime(timezone=True)` ✓ — no work.
- Numeric-as-string fields (`days_to_maturity`, `germination_time`, `indoor_start_time`, `level`, `amount_ml`): separate concern.
- Frontend: wire format stays ISO-8601 date strings in JSON, so `planting_date: string` in `frontend/src/api/plantTrackingAPI.ts` remains correct — no change expected (verify in planning).

## Constraints & Context

**Integration Points**:
- Both ORM model trees map the same `plants` table and must be updated atomically.
- API JSON contract is unchanged (ISO-8601 date strings on the wire).
- Cluster Postgres DB (`plant_tracking`) is the live data source; local dev DB (port 5433) is not currently running.

**Preferred Technologies**: Python/SQLAlchemy/Alembic — follow existing patterns.

**Constraints**:
- No data loss in the `planting_date` conversion.
- API and CLI behavior (what users type and see) is unchanged: `YYYY-MM-DD` in, `YYYY-MM-DD` out.

**End State**: `planting_date` and `death_date` are `date` objects in domain/ORM/Python, `DATE` columns in Postgres, and ISO strings only on the wire. The representation decision is recorded, so the review loop implements instead of re-litigating.

- Review feedback of the form "align death_date to String(10) to match the ORM" is superseded by this ticket's decision.
