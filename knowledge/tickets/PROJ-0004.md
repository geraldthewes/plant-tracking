# Handle different print formats

> **Workflow Status**: Requirements gathered ✓ → Ready for `/create_plan_generic` to research and plan

## Problem Statement & Business Context

**What problem are we solving?**
The current `create-label` and `print-label` commands hardcode the label print format to 40x30mm. A new roll of 50x70mm labels needs to be supported, which also requires a different orientation (longer dimension runs along the roll direction).

**Why is this important?**
- Immediate need: next roll of labels is 50x70mm format
- Future need: 50x30mm format support anticipated
- Paper costs money — combining image creation and printing into a single command reduces errors from mismatched formats
- Creating the image is fast, so the two-step workflow is inefficient

**Who needs this?**
Users printing plant identification labels.

## Reference Implementation (To Research)

**Location**: Existing `create-label` and `print-label` commands in the codebase

**Aspects to mimic**:
- Existing approach, library choices, and patterns must be preserved
- DO NOT change the approach — just parameterize the format and handle the new orientation

> Note: The original label implementation took significant effort to get right. Detailed analysis of the existing code will happen during the planning phase to understand how to safely extend it.

## Requirements & Scope

### Must-Have Features
- Support 40x30mm format (existing, unchanged behavior)
- Support 50x70mm format (new, different orientation: longer dimension along roll direction)
- Consolidate `create-label` and `print-label` into a single `print-label` command
- Add `--no-print` flag to `print-label` for image-only generation (no printing)

### Nice-to-Have Features
- Future-proof design to easily add 50x30mm and other formats later

### Out of Scope
- Format validation (user responsibility to match image format to physical label roll)
- Auto-detection of label format
- Changing the existing approach or libraries

## Constraints & Context

**Integration Points**: Existing printer interface and image generation pipeline

**Constraints**:
- Must follow the existing implementation approach — do not change libraries or patterns
- 50x70mm requires a different orientation than 40x30mm (longer dimension along roll direction)
- No validation — trust the user to choose the correct format

## Success Criteria

### Automated Verification
- [ ] `print-label` generates correct image for 40x30mm format
- [ ] `print-label` generates correct image for 50x70mm format (different orientation)
- [ ] `print-label` prints the generated label to the printer
- [ ] `print-label --no-print` generates image file only without printing
- [ ] Existing functionality is not broken

### Manual Verification
- [ ] Printed 40x30mm labels align correctly on physical labels
- [ ] Printed 50x70mm labels align correctly on physical labels (different orientation)

**End State**: Single `print-label` command that handles multiple formats with correct orientation, optional `--no-print` flag, and preserves all existing behavior.

## Research Questions for Planning Phase

The following should be investigated during `/create_plan_generic`:
- How are 40x30mm dimensions and orientation handled in the current implementation?
- How does the current printing pipeline work and how do we pass format to the printer?
- Where is the format hardcoded so we can parameterize it?
- How is image generation tied to format in the existing code?
- What changes are needed to support the different orientation for 50x70mm?

## Notes

- The original label implementation was complex and took significant effort. Be extra careful not to break existing functionality.
- 50x30mm format is anticipated for future but not required now.
