# Create python service package

> **Workflow Status**: Requirements gathered ✓ → Ready for `/create_plan_generic` to research and plan

## Problem Statement & Business Context

**What problem are we solving?**
The current business logic lives inside `commands/plant_tracking_cli.py` (~1422 lines, monolithic) with direct database calls. We need a shared Python service layer package so that both the FastAPI REST server (for the frontend web app) and CLI programs consume the same logic from one place.

**Why is this important?**
- Eliminates code duplication between CLI and API entrypoints
- Centralizes business logic for maintainability
- Enables proper architecture (Ports & Adapters / Hexagonal) per existing ADRs
- Supports streaming/iterator patterns for large responses (exports) so full payloads don't need to cross the API boundary

**Who needs this?**
- The CLI programs (refactored to consume the package)
- The FastAPI REST server (new entrypoint)
- Future consumers (e.g., Hermes agent integration)

## Requirements & Scope

### Must-Have Features
- **Domain models**: Pure Python classes for Plant, Genus, SeedPacket, PlantLog (no infrastructure imports)
- **Service layer**: Use-case functions that orchestrate business logic (CRUD, label generation, exports)
- **Repository adapter layer**: SQLAlchemy 2.0 + PostgreSQL with proper session management
- **Unit of Work pattern**: Transaction boundaries, commit/rollback
- **Label generation**: Full label generation logic (format, QR codes, layout) as part of service
- **Export capability**: Implemented as **iterator/streaming pattern** so full responses don't need to cross API boundary
- **All business logic**: Centralized in package; CLI and FastAPI are thin entrypoint shells only
- **Separate installable package**: `packages/plant_service/` with its own `pyproject.toml`
- **Testing**: Full test suite from day one (unit tests for domain/service, integration tests for adapters)
- **Linting & validation**: Type checking, linting, pre-commit hooks per best practices

### Nice-to-Have Features
- Fuzzy matching utilities (currently in CLI for genus search)
- Comprehensive error hierarchy with domain-specific exceptions

### Out of Scope
- FastAPI server implementation (separate work)
- CLI entrypoint implementation (separate work; will be refactored to consume this package)
- Phomemo printer hardware driver (external dependency, not service logic)
- Hermes agent integration
- Frontend application

## Constraints & Context

**Package Location**: `packages/plant_service/`

**Integration Points**:
- PostgreSQL database (existing)
- CLI programs in `commands/` (to be refactored)
- Future FastAPI server
- Alembic migrations (existing in repo root)

**Preferred Technologies**:
- Python 3.9+
- SQLAlchemy 2.0 (already in use)
- PostgreSQL (already in use)
- Hatchling build system (matches existing project)
- uv for package management (already in use)
- pytest for testing

**Constraints**:
- Follow Ports & Adapters / Hexagonal Architecture per ADR-0008
- Follow best practices from `software-backend-wiki`
- Dependency arrows point inward: adapters import domain, domain never imports adapters
- Export functions must use iterator/streaming pattern
- Separate installable package with its own `pyproject.toml`
- PostgreSQL best practices: connection pooling, proper session management, pool_pre_ping
