# FastAPI Backend to support home page

> **Workflow Status**: Requirements gathered ✓ → Ready for `/create_plan_generic` to research and plan

## Problem Statement & Business Context

**What problem are we solving?**
The plant tracking system currently has no web backend API. We need a FastAPI backend to serve the home page of the responsive web app described in the PRD and UX design specification.

**Why is this important?**
The web app is the primary user-facing interface for gardeners to track plants, log care activities, and access insights. The home page is the entry point for all garden interactions.

**Who needs this?**
Home gardeners using the responsive web app on mobile (in the garden) and desktop (for setup/management).

**Business value**
Enables the core user journey: open app on home screen → see what needs care → scan QR → log activity.

## Reference Implementation (To Research)

**Location**: `packages/plant_service/`

**Aspects to mimic**:
- Domain model structure (Plant, PlantLogEntry, etc.)
- Service layer pattern with repositories and unit of work
- Postgres adapter with SQLAlchemy ORM models

> Note: Detailed analysis of reference will happen during planning phase

## Requirements & Scope

### Must-Have Features

#### API Endpoint: `GET /api/plants/care-needed`
Returns plants needing care attention today with a count badge for the home screen.

- Query plants whose most recent care log is past a threshold
- Event types to consider: `water`, `fertilizer` (from `PlantLogEntry.VALID_EVENT_TYPES`)
- Return count of plants needing attention
- Return list of plant summaries (id, variety_name, what's overdue)
- Response time target: < 3 seconds (per NFR-PERF-01)

**Response shape** (tentative):
```json
{
  "count": 5,
  "plants": [
    {
      "plant_id": "HABY-2026-001",
      "variety_name": "Yellow Habanero",
      "overdue": [
        { "event_type": "water", "days_since": 3 }
      ]
    }
  ]
}
```

### Nice-to-Have Features
- Configurable care thresholds per event type (e.g., water every 2 days, fertilizer every 14 days)
- Seed packet specs (`days_to_maturity`, etc.) informing care schedule expectations

### Out of Scope
- Plant detail endpoint (`GET /api/plants/{plant_id}`) — deferred to plant detail page ticket
- Activity log endpoint (`GET /api/activity/recent`) — planned but not displayed on home page
- Auth/authentication — no auth for this iteration
- Photo upload, QR generation, label printing
- Hermes agent integration
- Create/update/delete endpoints
- Frontend implementation

## Constraints & Context

**Integration Points**:
- `plant_service` package (`packages/plant_service/`) — shared domain models, repositories, service layer
- Postgres database — existing schema via `plant_service` SQLAlchemy models

**Preferred Technologies**:
- FastAPI (Python) — per PRD tech stack
- Leverage existing `plant_service` package for data access

**Constraints**:
- Response time < 3 seconds for API calls (NFR-PERF-01 from PRD)
- Mobile-first responsive web app consumer
- No auth required at this stage
- Must reuse existing `plant_service` package — do not duplicate data access logic

## Success Criteria

### Automated Verification
- [ ] FastAPI server starts and responds to health check
- [ ] `GET /api/plants/care-needed` returns valid JSON response
- [ ] Response contains `count` and `plants` array
- [ ] Each plant object contains `plant_id`, `variety_name`, and `overdue` array
- [ ] Endpoint returns correct plants based on care log thresholds
- [ ] All automated tests pass
- [ ] Lint and type check pass

### Manual Verification
- [ ] Endpoint returns expected results against real database data
- [ ] Response time is under 3 seconds

**End State**: A minimal FastAPI service with the single `/api/plants/care-needed` endpoint, deployed and callable, using the existing `plant_service` package for all data access.
