# Add support for genus database

> **Workflow Status**: Implementation complete ✓ → Tests pending (see PROJ-0006)

## Problem Statement & Business Context

**What problem are we solving?**
Every time a new plant record is created via `python -m commands.plant_tracking_cli create-plant`, the gardener must re-enter the same variety name and Latin name repeatedly. For example, multiple Yellow Habanero plants all require re-typing "Yellow Habanero" and "Capsicum chinense."

**Why is this important?**
- Data consistency: Eliminates typos and spelling variations in Latin names across plant records
- Reduced friction: Fewer fields to enter speeds up plant creation
- Single source of truth: Genus info is maintained in one place, not duplicated across N plant records

**Who needs this?**
The gardener (sole user) who creates and manages plant records via the CLI.

## Requirements & Scope

### Must-Have Features
1. **Genus database** — Persistent store with two fields:
   - Common name (e.g., "Yellow Habanero")
   - Latin name (e.g., "Capsicum chinense")

2. **Updated `create-plant` flow** — Instead of entering common name + Latin name separately:
   - User enters/selects a common name
   - Genus is referenced by lookup, Latin name is retrieved automatically
   - Three paths: type a common name that exists, fuzzy-search to find existing, or create a new genus entry inline

3. **Fuzzy match search** — When entering a common name, suggest close matches to existing entries

4. **New CLI commands for genus management**:
   - List all genus entries
   - Add a new genus entry

5. **Label retrieval** — Latin name from genus database must be retrievable when generating labels

6. **Auto-migration** — Extract unique (common name, Latin name) pairs from existing plant records and populate the genus database automatically

### Nice-to-Have Features
- None at this time

### Out of Scope
- Web/mobile UI integration (CLI-only for now)
- Editing or deleting existing genus entries
- Importing genus entries from external files
- Additional genus fields (species, family, care requirements, etc.)

## Constraints & Context

**Integration Points**:
- `plant_tracking_cli` command-line interface
- Existing plant record storage (markdown/JSON)
- Label generation system (needs Latin name lookup)

**Preferred Technologies**:
- Python (existing codebase)
- Follow existing patterns from seed packet database implementation

**Constraints**:
- Must preserve all existing plant data during migration
- Migration should be idempotent (safe to re-run)
- CLI flow should remain fast — no blocking operations
