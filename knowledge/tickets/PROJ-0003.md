# Date fixes on plant database

> **Workflow Status**: Requirements gathered ✓ → Ready for `/create_plan_generic` to research and plan

## Problem Statement & Business Context

**What problem are we solving?**
Two bugs in the plant schema and CLI tool related to date handling.

**Why is this important?**
1. The `planned_planting_date` field name is verbose and inconsistent — should be simply `planting_date`.
2. Plant IDs are generated using the current year instead of the planting date year, producing incorrect IDs for historical or backdated records. Example: a record planted in 2024 created in 2026 gets `YEHA-2026-001` instead of `YEHA-2024-001`.

**Who needs this?**
Users managing plant records, especially those adding historical planting data.

## Requirements & Scope

### Must-Have Features
- Hard rename `planned_planting_date` → `planting_date` across schema and CLI tool
- Migration: update all existing plant records to use the new field name
- Fix plant ID generation to derive the year from `planting_date`, not the current year

### Nice-to-Have Features
- Validation on `planting_date` format during record creation

### Out of Scope
- Retroactive fix of existing plant IDs (existing IDs like `YEHA-2026-001` remain as-is since labels are already in use)
- Frontend display changes (not known to be affected)

## Constraints & Context

**Integration Points**: Plant database schema, CLI tool

**Preferred Technologies**: Existing tech stack

**Constraints**:
- Existing plant IDs must not be changed
- Migration must preserve all data

## Success Criteria

### Automated Verification
- [ ] Schema reflects `planting_date` field (no `planned_planting_date`)
- [ ] All existing plant records migrated successfully
- [ ] New records with a `planting_date` in year Y get IDs with year Y
- [ ] All automated tests pass

### Manual Verification
- [ ] Create a plant record with a past `planting_date` and verify ID year matches
- [ ] Inspect a migrated record to confirm field rename

**End State**: Schema uses `planting_date`, all records migrated, ID generation uses planting year for new records.

The following should be investigated during `/create_plan_generic`:
