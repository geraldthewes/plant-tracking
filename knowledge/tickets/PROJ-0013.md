# Mark plant as dead

> **Workflow Status**: Requirements gathered ✓ → Ready for `/create_plan_generic` to research and plan

## Problem Statement & Business Context

**What problem are we solving?**
Sam the gardener needs to record when a plant has died — capturing the date of death and reason — while keeping the record in the system for future analysis.

**Why is this important?**
Tracking plant mortality enables analysis of what's working and what isn't (pests, watering habits, timing, etc.). Dead plants need to be distinguishable from active plants in listings.

**Who needs this?**
Sam the gardener.

## Requirements & Scope

### Must-Have Features
- Add `death_date` field to plant record (date, required when plant is marked dead)
- Add `death_reason` field to plant record with predefined options:
  - Pest infestation
  - Disease
  - Overwatering
  - Underwatering
  - Frost/cold damage
  - Heat stress
  - Transplant shock
  - Drought
  - Unknown
  - Other (requires a free-text comment)
- Add `death_comment` field to plant record (optional free text, required if reason is "Other")
- CLI command to mark a plant as dead (date + reason + optional comment)
- API endpoint to mark a plant as dead
- Filter plant listings by alive/dead status
- Dead plant records persist in database for historical analysis

### Nice-to-Have Features
- None for this iteration

### Out of Scope
- Bulk operations
- Graveyard visualization
- Mortality statistics/dashboards
- Archival to cold storage
- Notifications

## Constraints & Context

**Integration Points**:
- Domain model, ORM model, service layer, repository, API routes, CLI, frontend API
- Alembic database migration

**Preferred Technologies**: Python/SQLAlchemy/Alembic (backend), TypeScript (frontend) — follow existing patterns.

**Constraints**:
- Records must persist (no soft delete that removes data)
- "Other" death reason must require a comment
