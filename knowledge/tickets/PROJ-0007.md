# Migrate from Markdown file storage to PostgreSQL

> **Workflow Status**: Requirements gathered ✓ → Ready for `/create_plan_generic` to research and plan

## Problem Statement & Business Context

**What problem are we solving?**
The project currently stores all data (plants, logs, seed packets, genera) as Markdown files on disk. This needs to migrate to PostgreSQL for structured querying, scalability, and eventual multi-client support.

**Why is this important?**
File-based storage doesn't scale for querying, aggregation, or future features. Markdown format will be preserved for export but Postgres becomes the source of truth.

**Who needs this?**
Primary user — the CLI operator. Future web/mobile clients and Hermes agent (FR36-FR41) will share the same database.

**PRD Context**: This is Phase 3 (Expansion) per PRD, item FR51: "Migrate data from markdown to Postgres database format." Architecture already specifies PostgreSQL 15 as the primary data store (`knowledge/architecture/database/c2-container.md`).

## Requirements & Scope

### Must-Have Features
- SQLAlchemy ORM models for all entities: plants, logs, seed packets, genera
- Database connection layer with configurable connection string
- CLI commands updated to read/write from Postgres instead of Markdown files
- Import job to migrate all existing Markdown data to Postgres
- Markdown export preserved (write path remains)

### Nice-to-have Features
- Rollback utility to export entire DB back to Markdown format
- Connection health check command
- FastAPI backend service for Hermes agent API access (FR41)

### Out of Scope
- Supabase-specific features (auth, real-time, edge functions)
- Pinecone vector store for semantic search (architecturally specified but not needed for CLI)
- Web UI or API server (deferred to later phase)
- Multi-tenant support
- Redis queue for Hermes analysis (architecture-specified, deferred)

## Constraints & Context

**Integration Points**: Self-hosted local PostgreSQL instance

**Preferred Technologies**:
- SQLAlchemy ORM
- Python 3.12+, uv package manager
- Existing project conventions (ruff, black, mypy, pytest)

**Constraints**:
- Self-hosted Postgres locally (no cloud dependency)
- Must support idempotent import (re-runnable without duplicates)
- Zero data loss during migration

## Research Questions for Planning Phase

The following should be investigated during `/create_plan_generic`:
- SQLAlchemy sync vs async for CLI context — which fits existing code better?
- Connection/session management pattern (per-command session vs pooled engine)?
- Database migration tooling — Alembic for schema versioning (architecture mentions Flyway-style migrations)
- Complete schema design for all four entity types and their relationships
- Import job architecture: parsing strategy, error handling, idempotency mechanism
- How to handle the `database/` directory during/after migration (deprecate, keep as backup)?
- Environment variable for DATABASE_URL configuration (architecture specifies `DATABASE_URL`)
- How to model the PlantLogEntry consolidated log file as a relational table
- How to handle the plant ID generation (`VARIETY-YYYY-SEQ`) in DB vs file-based approach
- Architecture specifies connection pooling (min=2, max=20) — align with this
- How to handle the `find_next_sequence` pattern in DB vs filesystem scan
