# Standardize CLI error handling and logging per ADR-0009

> **Workflow Status**: Requirements gathered ✓ → Ready for `/create_plan_generic` to research and plan

## Problem Statement & Business Context

**What problem are we solving?**

ADR-0009 (`knowledge/architecture/decisions/ADR-0009-CLI-error-handling-and-logging-conventions.md`) established the CLI error-handling and logging conventions, and the accompanying cleanup removed the last `traceback.print_exc()` call and the dead `import traceback`. Four residual gaps remain in `commands/plant_tracking_cli.py`:

1. **No logging infrastructure** — the CLI configures no `logging` at all; an unexpected error leaves no record beyond the one-line message shown to the user.
2. **Inconsistent exit codes** — `mark_dead`, `show_*`, and `create_*` commands call `sys.exit(1)` on failure, but `log_*` and `media_*` commands print an error and return normally (exit code 0), so scripts and cron jobs cannot detect their failure.
3. **Silent exception swallowing** — eleven lookup/verification paths use bare `except Exception: pass` (genus and seed-packet lookups in `create_plant`, duplicate checks in `create_seed_packet`/`create_genus`, plant-exists checks in the `log_*`/`media_*` commands), violating the project guideline to never swallow exceptions without logging.
4. **No detail recorded for unexpected errors** — the final `except Exception` handlers print `✗ ...: {e}` but record nothing.

**Why is this important?**

Failure visibility and scriptable CLI behavior. Without exit codes, unattended runs (label printing from cron, batch logging) silently no-op on failure; without logs, diagnosing "Unexpected error" requires reproducing it.

## Requirements & Scope

### In Scope

| # | Change | Location | Testing strategy |
|---|---|---|---|
| 1 | Configure stdlib `logging` once in `main()`: logger `plant_tracking.cli`, `StreamHandler` to **stderr**, format `%(asctime)s %(levelname)s %(name)s: %(message)s`, level from `PLANT_TRACKING_LOG_LEVEL` env (default `INFO`) | `main()` in `commands/plant_tracking_cli.py` | Red/Green — new test: with `PLANT_TRACKING_LOG_LEVEL` unset, an unexpected exception logs to stderr via the configured handler (caplog) |
| 2 | `logging.exception(...)` in every final `except Exception` handler of command handlers (user still sees only the concise `✗` line) | all command handlers | Red/Green — extend existing `TestMarkDeadCLI.test_unexpected_error_from_update` pattern to assert a log record with traceback |
| 3 | `log_*` and `media_*` failure paths: `return` → `sys.exit(1)` after printing the error (behavior change; user-initiated cancellations such as `create_seed_packet`'s "Create anyway? N" stay exit 0) | `log_humidity`, `log_water`, `log_fertilizer`, `log_note`, `media_add_attachment`, `media_list_attachments`, `media_show_attachment`, `media_delete_attachment`, `media_get_url` | Red/Green — new tests asserting `SystemExit(1)` on each simulated failure path |
| 4 | Replace the eleven `except Exception: pass` blocks with `logging.getLogger(__name__).warning(...)` including the exception context and the operation that failed (behavior: the fallback paths still run) | see locations in Problem Statement | New tests only — verify a warning is logged for one representative silent path per command family and that the fallback still executes |

### Out of Scope

- FastAPI entrypoint (has its own exception handling and logging).
- A shared error-handling utility/decorator module (rejected in ADR-0009 alternatives; revisit only if the CLI splits into multiple modules).
- Pre-existing ruff/mypy/black findings in `commands/` (25 ruff, 12 mypy, 1 black deviation) — separate cleanup ticket if wanted.

## Constraints & Context

**Integration Points**:
- `main()` is the only logging configuration point; command handlers must not reconfigure logging.
- Stdout remains command output only; all logs go to stderr so piped output stays clean.
- Exit-code change (item 3) is observable to any existing cron/script callers.

**Constraints**:
- Stdlib `logging` only — no new dependencies.
- No change to user-visible success output.

## Success Criteria

### Automated Verification
- [ ] A failing test is written and passes for each of items 1-3 (Red/Green)
- [ ] A warning is logged for the representative silent paths of item 4 and fallbacks still execute
- [ ] `pytest tests/` fully green (baseline: 100 passed)
- [ ] No new ruff/mypy errors vs. baseline (25 ruff / 12 mypy)
- [ ] `traceback.print_exc` count remains 0 in the codebase

### Manual Verification
- [ ] `plant-tracking log humidity <nonexistent> --level 5; echo $?` prints the error and exits 1
- [ ] `PLANT_TRACKING_LOG_LEVEL=debug plant-tracking mark-dead <id>` logs with traceback to stderr on a forced failure; user sees only the `✗` line

**End State**: every CLI failure exits non-zero, every unexpected error is logged with full detail on stderr, no exception is swallowed silently, and the ADR-0009 conventions are fully implemented and test-covered.
